1. Performance Evaluation

How would you evaluate the performance of the agents on each ticket and why?

#AI Explanation:

  • SKU, size and quantity: exact. Ticket 101 asked for CC-TEE-WHITE, size S, qty 1 and the agents found 0 on hand. Ticket 103 asked for 20 CC-HOOD-NAVY in size M, found 8 on hand, and the restock request is for exactly the 12-unit shortfall.
  • Vendor and lead time: exact. Both restocks went to Bulldog Print Co (apparel reprint, 5 days), not Elm City Gifts (mugs, 3 days) or QuickShip CT (courier, 1 day). Expected arrival 2026-09-05 is 2026-08-31 plus 5, and the customer drafts call it an estimate that is not assured.
  • Prices and money: exact. Hoodie unit cost $22, list $58 (62.1% margin). The proposal of $52.20 is exactly 10% off, and its 57.9% margin equals (52.20 − 22) / 52.20. Invoice 501 was $840 due 2026-08-28; rent was $2,400 due 2026-09-02; the Cash tab ties out ($3,400 − $840 − $2,400 = $160).
  • Minimum order quantity: not measured. This build has no shop handbook file and no min-order or vendor-fee column; the only vendor attributes are specialty and lead_days. A 1-unit tee restock from Bulldog Print Co looks fine here but a real vendor minimum could reject it. That is a blind spot, not a pass.
  • Purchasing rules held. Both restocks were saved as blocked_unpaid_invoice and named invoice 501; they only became proposed after a human approved the $840 payment. Neither payment request overdrew checking ($3,240 of $3,400 requested). Zero payments were made by an agent, the two payments and the discount carry Blessy Bellamy's name, and the two customer replies are drafts (sent: false).
  • Weaknesses found. (a) The customer draft for 101 tells Tauhid that the printer is waiting on an invoice payment, which is internal information the prompt asked Customer Service to keep out. (b) Nothing checks restock cost against cash: after rent and invoice 501, $160 is left, but 12 hoodies at $22 unit cost is $264. (c) In the first full run, Accounting skipped the discount proposal on 103, which cost about 113,800 discarded tokens before I tightened its prompt.
  • Prompt injection: not tested, protected by design. The three tickets had benign text and I did not run an adversarial ticket. What the execution data does show: 286 audit events after the reset contain no call to approve_payment, reject_payment or the price-approval tools; none of those is in any agent's tool list; no send_email tool exists on the server; and calling approve_payment from an agent-style server returns "payments can only be decided by a human". So an injected instruction could not move money even if a model obeyed it. Untested: injected text inside ticket notes, and draft_customer_message accepts any recipient string, which would matter the day a send tool is added.

#Student Explanation:

The agent did a good job with performing the task. For 101 - the boss accurately called inventory first, found the correct stock for SKU CC-TEE-WHITE, size S, qty 1, then delegated to accounting to inspect the invoice, then asked for human approval. For the other tickets, it also adhered to the purchasing rules. All payments stayed within the available balance. It did not send direct customer emails or auto-approve payments.

3. Single Agent vs. Multi-Agent

What would have been simpler as one agent with tools — and why?

#AI Explanation:

  • What the numbers say. The three main runs used 117,361 tokens over 55 model requests, about 2,100 tokens per request, and the follow-up passes added 50,144 more. Each agent re-sends its own prompt and its tool list on every request. The five prompts total about 13 KB (roughly 3,300 tokens). There is no handbook index in this build, so that re-sent prompt text is the real per-call overhead.
  • Redundant reads from handoffs. Across the three tickets, get_ticket was called 15 times (4, 5 and 6 per ticket), get_today 9 times and list_payment_requests 11 times, because every agent re-reads what the last one already knew. Accounting ran twice on both 101 and 103 (once from the Boss, once from Inventory's handoff).
  • Rent (ticket 102) as one agent. The real work is 3 tool calls (get_lease, get_cash_balance, request_payment). One agent with those tools would need roughly 4 or 5 model requests; the team used 14 requests. This is my estimate from call counts, not a measured run.
  • Discount quote as one agent. get_pricing → check_discount → propose_price_override is a fixed 3-call routine that does not need Inventory or Customer Service to take part.
  • Vendor-block-to-payment-request. The Inventory → Accounting handoff on 101 and 103 exists to run one request_payment for invoice 501. Giving Inventory a read-only invoice check and letting the Boss call Accounting once would remove the duplicate Accounting run.
  • Handoff friction in Customer Service. Because reports reach it as prose, it re-verifies with check_stock, get_pricing and list_vendors before writing (9 actions on each of 101 and 103). A typed structure passed forward would let it skip those.
  • Where multi-agent earns its cost. Not speed but separation of authority: only Accounting can create a payment request, only Customer Service can save a draft, and no agent holds an approval tool. I would keep those permission boundaries and merge the read-and-prepare routines around them.

#Student Explanation:

The benefits of the single agent is that because there is only one agent in the loop, there are fewer calls and therefore lower costs. If there is a technical issue, it is easier to identify the source of the bug because there is one source. In contrast, with multi-agent systems because each agent makes calls, it quickly can use tokens.

4. Solvable New Problems (Existing Tools)

Describe three new problems Campus Customs might face that this agent team could solve with the tools you built.

#AI Explanation:

  • Note on the toolset. What exists is the MCP read and write tools, Pydantic-validated agent reports (SpecialistReport, TicketOutcome), and the server-side rule guards. The HTML/PDF/.eml parsers and a handbook compliance checker are not built here, so the three ideas below use only what is.
  • 1. Weekly overdue-invoice and cash sweep. list_invoices (overdue_only), get_cash_balance and request_payment already let Accounting find every open invoice past desk.date_today, compare the total with checking and queue requests in priority order. With $3,400 in checking and $3,240 already claimed, it would show a human exactly how little room is left.
  • 2. Catalog-wide restock planner. list_inventory, list_vendors and create_restock_request can scan every SKU and size, flag shortfalls like CC-TEE-WHITE S (0 on hand) or CC-HOOD-NAVY M (8 on hand), pick the vendor by specialty, and quote arrival as today plus lead_days (5, 3 or 1) while marking anything blocked by an open invoice.
  • 3. Club bulk-quote desk. get_pricing, check_discount and propose_price_override can answer any bulk request: list margins today are 71.4% (tee), 72.7% (cap), 75.0% (mug) and 62.1% (hoodie), so the agent can show the price at which each margin falls and save one proposal. It still needs a stated minimum-margin policy, which the shop has not defined.

#Student Explanation:

Using our existing tools and database schema, Campus Customs can immediately solve:

  1. Highest Discount Analysis: Querying the price_proposals table, with list prices from the pricing table, to identify which items have the largest proposed price overrides or highest percentage discounts.
  2. Vendor Outstanding Payment Monitoring: Querying the invoices and vendors tables to flag all unpaid vendor balances and identify which suppliers require payment before new inventory orders can be placed.
  3. Out-of-Stock Item Alerts: Checking the inventory table across all product SKUs and sizes to instantly generate a report of items with zero stock on hand.

5. Unsolvable Problems (Required New Tools & Agents)

Describe three new problems Campus Customs might face that this agent team could not solve with the tools you built, and explain the tools and agents you would need to solve them.

#AI Explanation:

  • 1. Actually placing and tracking vendor orders. Today a restock is only a proposal and no vendor is contacted. Needed: a vendor_terms table (min order quantity, setup and rush fees, ship cost) and tools place_purchase_order, get_order_status and a payment-gateway adapter that executes approved payments. Architecture: a Purchasing agent that builds the order and a separate Order-Tracking agent, with the human seal kept in front of every spend, idempotency keys so a retry cannot double-pay, and a per-order spend cap.
  • 2. Reading real vendor invoices and quotes that arrive by email or PDF. Invoice 501 was seeded in the database; in real life it would arrive as a PDF or .eml. Needed: an inbox connector (IMAP or Gmail API), an HTML/PDF/.eml parser with OCR, a Pydantic extraction schema with per-field confidence, an injection-scrubbing step, and a match-to-purchase-order tool. Architecture: a quarantined Intake agent with no write tools, then a Validation agent, then Accounting; text from outside never reaches an agent that holds a payment or draft tool.
  • 3. Forecasting demand around the campus calendar. The team reacts to one customer ticket at a time and cannot know that hoodie demand rises before the Yale AI Club-style bulk orders. Needed: a sales-history connector (POS export or store API), a calendar of move-in and event dates, a forecast tool, and a reorder-point optimizer that accounts for the 5-day Bulldog Print Co lead time. Architecture: a read-only Analyst agent over sales data feeding a Planner agent that proposes restocks, plus an evaluation harness that replays past semesters to score forecast error before anyone trusts it.

#Student Explanation:

Three business problems Campus Customs cannot solve with the current toolset include:

  1. Gift Card Balance Lookups: The current database lacks a gift_cards table or ledger, so agents have no way to query or track gift card balances for customers.
  2. Customer Purchase Refund Processing: Processing a refund requires an external payment gateway API integration (like Stripe or PayPal) to send money back to customer accounts, whereas our current tools only read local cash balances and prepare manual outbound business payments.
  3. Lease Renewal & Document Signing: Signing lease paperwork requires an e-signature API (like DocuSign) and legal document generation tools, as well as external communication capabilities that bypass our local board-only restriction.
